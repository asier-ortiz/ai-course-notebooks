1. Entendimiento del Negocio y Diseño del Caso de Uso

1.1. Contexto y Objetivo

El mercado de alquiler en Madrid presenta desafíos significativos tanto para inquilinos como para propietarios a la hora de establecer precios justos y transparentes. El objetivo de este proyecto es desarrollar un sistema de Machine Learning end-to-end que prediga con precisión el precio de alquiler de una propiedad basándose en sus características específicas, cubriendo todo el rango de precios del mercado madrileño.

Este sistema permitirá:

  • A los inquilinos: evaluar si un precio de alquiler es justo según las características de la propiedad
  • A los propietarios: establecer precios competitivos y realistas
  • A profesionales inmobiliarios: disponer de una herramienta de valoración automatizada
  • Al mercado en general: mayor transparencia en la formación de precios
Objetivo del Sistema: Desarrollar un sistema ML end-to-end que permita predecir precios de alquiler de manera precisa y transparente para todo el mercado madrileño.

1.2. Justificación del Dataset

Se utiliza el dataset de alquileres de Madrid obtenido de Kaggle, que contiene información exhaustiva sobre propiedades en alquiler. El dataset original contiene 9.229 registros con 34 variables que cubren características físicas, equipamiento, ubicación y precios de todo el mercado madrileño.

Enriquecimiento geográfico previo: Como trabajo preparatorio en fases anteriores del proyecto, se añadieron al dataset original las coordenadas geográficas (latitud y longitud) utilizando la API de Google Maps. Este proceso se realizó mediante código personalizado que procesó las direcciones disponibles en las columnas de ubicación existentes para obtener las coordenadas precisas.

Este dataset es ideal para el caso de uso porque:

  • Datos reales y actualizados: Información extraída de portales inmobiliarios activos
  • Cobertura completa: Representa todo el rango de precios del mercado madrileño
  • Variables relevantes: Incluye factores determinantes del precio como ubicación, superficie y equipamiento
  • Volumen adecuado: Suficientes registros para entrenamiento robusto de modelos ML
  • Información geográfica enriquecida: Coordenadas precisas obtenidas via Google Maps API permiten cálculos de distancia y análisis de ubicación
Procesamiento en AWS: Todo el procesamiento de datos (limpieza, transformación, feature engineering) se realizará utilizando las herramientas de AWS SageMaker, específicamente Data Wrangler, como parte del pipeline ML end-to-end.

2.3. Análisis de Target Leakage

Se realizó un análisis exhaustivo de target leakage utilizando SageMaker Data Wrangler para detectar variables que podrían contener información que no estaría disponible al momento de hacer la predicción o que duplican indirectamente la variable objetivo. El análisis evalúa la capacidad predictiva individual de cada variable mediante validación cruzada en una muestra de 1.000 registros.

Figura 2: Análisis de target leakage - Capacidad predictiva individual por variable

Interpretación de Resultados

Escala de interpretación (R²):

  • 1.0: Target leakage perfecto - Variable idéntica al target
  • 0.7-0.9: Likely target leakage - Probable filtración
  • 0.5-0.7: Possibly target leakage - Posible filtración
  • 0.2-0.5: Safe - Variables seguras con correlación normal
  • 0.0-0.2: Possibly redundant - Posiblemente redundantes

Variables Analizadas y Resultados

Variables SEGURAS (R² < 0.5):

  • Variables de estructura física: floor_built, bathrooms, bedrooms (~0.45-0.5) - Correlación alta pero esperada
  • Variables de ubicación: subdistrict, floor_area, type (~0.3-0.4) - Relación lógica con el precio
  • Variables de equipamiento: lift, air_conditioning, garage_included (~0.25-0.35) - Impacto moderado esperado
  • Variables geográficas: district, lat, lng, location (~0.2-0.3) - Correlación geográfica normal

Variables PROBLEMÁTICAS (R² cercano a 0):

  • Variables de metadatos: url, title, last_update, web_id - Muy baja capacidad predictiva
  • Variables redundantes: furnished, equipped_kitchen, year_built - Posiblemente redundantes
  • Candidatas a eliminación: orientation, garden_area, terrace - Aporte mínimo al modelo

Conclusión del Análisis: No se detectó target leakage significativo en el dataset. Las variables con mayor capacidad predictiva (floor_built, bathrooms, bedrooms) muestran correlaciones lógicas y esperadas con el precio de alquiler. Las variables con R² muy bajo son candidatas para eliminación en la fase de feature selection para optimizar el modelo.
Recomendaciones:
  • Eliminar variables de metadatos (url, title, web_id) que no aportan valor predictivo
  • Evaluar la utilidad de variables con R² < 0.1 como orientation y garden_area
  • Mantener todas las variables con R² > 0.2 ya que representan relaciones legítimas
  • Considerar feature engineering para maximizar el valor de variables con correlación moderada

3.1. Transformaciones Implementadas

Se aplicaron las siguientes transformaciones secuenciales para preparar los datos:

Paso Transformación Descripción Justificación
1 Custom Formula - Distancia al Centro Creación de columna distance_to_center usando fórmula de Haversine Variable geográfica relevante para el precio
2 Drop Columns Eliminación de 12 columnas no relevantes Reduce dimensionalidad y ruido
3 Custom Formula - Imputación Creación de floor_area_estimate para valores faltantes usando metros totales Preserva información de variable altamente correlacionada
4 Drop Column - floor_area Eliminación de columna original Evita duplicación tras imputación
5 Drop Missing Eliminación de filas con valores faltantes Garantiza calidad final del dataset

Detalle de Transformaciones Aplicadas

1. Creación de Variable de Distancia al Centro

Fórmula utilizada (Haversine):

6371 * acos( cos(radians(40.416775)) * cos(radians(lat)) * cos(radians(lng) - radians(-3.703790)) + sin(radians(40.416775)) * sin(radians(lat)) )
  • Coordenadas de referencia: Puerta del Sol (40.416775, -3.703790)
  • Resultado: Distancia en kilómetros desde el centro de Madrid
  • Beneficio: Captura el efecto de la ubicación en el precio de manera cuantitativa

2. Eliminación de Columnas No Relevantes

Columnas eliminadas: deposit, lat, lng, postalcode, year_built, web_id, last_update, orientation, professional_name, subdistrict, title, url

  • Variables de metadatos: web_id, title, url, last_update, professional_name
  • Variables geográficas redundantes: lat, lng (ya procesadas en distance_to_center), postalcode, subdistrict
  • Variables con baja correlación: deposit, year_built, orientation (según análisis previo)

3. Imputación Inteligente de Superficie

Estrategia de imputación:

CASE WHEN floor_area IS NULL THEN floor_built * 0.75 ELSE floor_area END
  • Lógica: Estima superficie útil basándose en superficie total construida
  • Factor 0.75: Relación empírica entre metros construidos y metros útiles
  • Preservación de datos: Mantiene valores originales cuando están disponibles
  • Diferencia clave: floor_built = metros totales construidos, floor_area = metros útiles

Procesamiento Automático en Autopilot

SageMaker Autopilot maneja automáticamente:

  • Codificación de variables categóricas: Autopilot identifica automáticamente las variables categóricas y aplica las técnicas de encoding más adecuadas (one-hot encoding, target encoding, etc.) según el contexto del problema
  • Normalización de datos: Escalado automático de variables numéricas según el algoritmo seleccionado
  • Selección de características: Evaluación automática de la importancia de las características y selección óptima
  • División train/test: Creación automática de splits de entrenamiento y validación sin intervención manual
  • Detección de tipo de problema: Identificación automática del tipo de problema (regresión) basándose en la variable objetivo
Ventaja de Autopilot: SageMaker Autopilot se encarga del preprocesamiento de datos automáticamente. No es necesario realizar técnicas convencionales de preprocesamiento como el manejo de valores faltantes, conversión de características categóricas a numéricas, escalado de datos, y manejo de tipos de datos más complicados.
Dataset Listo: El conjunto de datos madrid_rent_cleaned.csv está optimizado y listo para ser procesado por SageMaker Autopilot, que aplicará automáticamente todas las transformaciones adicionales necesarias según los algoritmos seleccionados.

Imputación Avanzada de Variables Faltantes

En trabajos anteriores con este mismo dataset, implementé un modelo de regresión específico para imputar los valores faltantes de la columna floor_area, aprovechando su alta correlación con el precio objetivo. En proyectos anteriores he trabajado con datasets que incluían estas descripciones, las cuales contienen información valiosa sobre características de la propiedad, estado de conservación, y elementos diferenciadores que impactan el precio.

  • EDA automático comprehensivo: Data Wrangler proporcionó análisis exploratorios increíblemente detallados, incluyendo detección de target leakage, análisis de correlaciones, y reportes de calidad de datos que habrían requerido días de trabajo manual
  • Gestión completa del ciclo de vida: Desde el análisis inicial hasta el despliegue y monitorización, todo integrado en una plataforma unificada
  • Escalabilidad automática: Capacidad de manejar datasets de cualquier tamaño sin preocupaciones por infraestructura
  • Integración nativa: Conectividad perfecta entre S3, CloudWatch, Model Registry y otros servicios AWS

Principal Limitación: Costos Elevados

La única desventaja significativa de AWS SageMaker es su alto costo. Para proyectos académicos o pequeñas empresas, los precios pueden ser prohibitivos:

  • Instancias de entrenamiento desde $0.50/hora para las más básicas
  • Endpoints en tiempo real con costos fijos independientemente del uso
  • Servicios adicionales como Clarify, Model Monitor, y Ground Truth con tarifas premium

Esta limitación económica impactó directamente el alcance del proyecto, impidiendo la implementación de funcionalidades avanzadas como análisis un de sesgo más completo con Clarify o la creación de endpoints en tiempo real.
